# Feature 3.6-b — Bulk Verify Credentials API Documentation

> **Portal**: Verifier
> **Base Path**: `/api/v1`
> **Auth**: `Authorization: Bearer <JWT_TOKEN>` (Verifier institution account)
> **Feature**: Synchronous bulk credential verification via CSV upload

---

## Overview

The Bulk Verify Credentials feature allows authenticated Verifier users to upload a CSV file containing up to 500 verification codes (one per row) and receive a single synchronous response containing a per-row outcome and a batch-level summary. Each row is evaluated using the same verification logic as the single-verify endpoint (2.9): expiry, revocation, access-count, and organization-restriction checks. The Trusted Organizations setting on each VerifiedLink controls access: when **OFF** (`allowed_org_ids` is empty), any authenticated Verifier can verify the code; when **ON** (`allowed_org_ids` is non-empty), only listed organizations can verify. Only fully successful rows — `status: "active"` and `is_restricted: false` — result in an access-log entry being written and `remaining_access_count` being decremented.

---

## 1. Verifier Endpoints

### 1.1 Bulk Verify Codes

> **`POST /api/v1/verifier/verified-links/bulk-verify`**
> **Summary**: `[Verifier] Bulk Verify Codes`
> **Auth**: Verifier institution account (Bearer JWT)

Accepts a multipart/form-data CSV file upload containing one plaintext verification code per row. Processes every non-blank row synchronously using the same check sequence as the single-verify endpoint and returns a complete per-row result set with a batch summary. Blank/whitespace-only rows are silently skipped and do not appear in the results.

#### Request Body

`Content-Type: multipart/form-data`

| Field | Type | Required | Description |
|---|---|---|---|
| `file` | File (CSV) | Yes | Single-column CSV file, one verification code per row, no header required. Max 500 non-blank rows. |

**CSV format example**:
```
A3F9-K2LP
B7MN-P9QR
C1XZ-T4WV
INVALID-CODE
```

**Response `data` field breakdown**:

| Field | Type | Description |
|---|---|---|
| `batch_id` | String (UUID4) | Server-generated identifier for this batch request. Not persisted. |
| `total` | Integer | Count of non-blank rows processed. |
| `summary.active` | Integer | Rows with status `"active"` (includes restricted). |
| `summary.expired` | Integer | Rows with status `"expired"` (includes exhausted access count). |
| `summary.revoked` | Integer | Rows with status `"revoked"` (link or credential revoked). |
| `summary.not_found` | Integer | Codes with no matching VerifiedLink record. |
| `results[].row_number` | Integer | 1-indexed row position in the uploaded CSV (blank rows not counted). |
| `results[].code` | String | The plaintext code as submitted in the CSV. |
| `results[].status` | String | `"active"` / `"expired"` / `"revoked"` / `"not_found"` |
| `results[].is_restricted` | Boolean | `true` only when `status == "active"` AND the caller org is not in `allowed_org_ids`. |
| `results[].credential_id` | String or null | Set only for active + non-restricted rows. |
| `results[].owner_name` | String or null | Credential holder full name. Set only for active + non-restricted rows. |
| `results[].credential_type` | String or null | Degree/credential type label. Set only for active + non-restricted rows. |

**Organization-restricted row example** (`is_restricted: true`):

```json
{
  "row_number": 2,
  "code": "B7MN-P9QR",
  "status": "active",
  "is_restricted": true,
  "credential_id": null,
  "owner_name": null,
  "credential_type": null
}
```

> The VerifiedLink has **Trusted Organizations ON** (`allowed_org_ids` is non-empty) and the caller's organization is not in the allowed list. The code itself is valid (unexpired, unrevoked), but this Verifier is not permitted to access it. No access log entry is written and `remaining_access_count` is NOT decremented.
>
> When **Trusted Organizations is OFF** (`allowed_org_ids` is empty), the code is open to all authenticated Verifiers and `is_restricted` will always be `false`.

#### Error Responses

- `422 BULK_VERIFY_ROW_LIMIT_EXCEEDED` — CSV contains more than 500 non-blank rows. No rows are processed.
- `400 INVALID_CSV_FILE` — Uploaded file cannot be parsed as CSV, or contains zero non-blank rows.
- `401 UNAUTHORIZED` — Missing or invalid Bearer token, or caller is not a Verifier institution account.

## 2. Denial / Failure Scenarios Table

Per-row outcomes are NOT HTTP errors. Every row produces a result entry in the results array. The table below describes what triggers each status value.

| Scenario / Trigger | Row status | is_restricted | Access Log Written? |
|---|---|---|---|
| Active, non-restricted VerifiedLink | `"active"` | false | Yes |
| Active VerifiedLink with Trusted Orgs **ON** (`allowed_org_ids` non-empty), caller org not in the list | `"active"` | true | No |
| VerifiedLink with `status == "revoked"` | `"revoked"` | false | No |
| VerifiedLink with `expires_at` in the past | `"expired"` | false | No |
| VerifiedLink with `remaining_access_count == 0` | `"expired"` | false | No |
| VerifiedLink whose Credential is revoked | `"revoked"` | false | No |
| Code has no matching VerifiedLink record | `"not_found"` | false | No |

**Request-level errors** (whole request rejected, no rows processed):

| Trigger | HTTP Status | error_code | message |
|---|---|---|---|
| CSV has more than 500 non-blank rows | `422` | `BULK_VERIFY_ROW_LIMIT_EXCEEDED` | Row limit exceeded. Max 500 codes per request. |
| File is not parseable CSV or has zero non-blank rows | `400` | `INVALID_CSV_FILE` | Invalid or empty CSV file. |
| Not authenticated or not a Verifier account | `401` | `UNAUTHORIZED` | Authentication required. |

## 3. Business Rules Summary

1. **Synchronous processing only** — one request, one response. No polling or job IDs.
2. **Row limit**: 500 non-blank codes per request. Blank/whitespace rows are silently skipped.
3. **Status taxonomy**: `active` / `expired` / `revoked` / `not_found`. "Exhausted" (access count = 0) maps to `expired`.
4. **`is_restricted`** is determined by the **Trusted Organizations** setting on the VerifiedLink, not by the credential itself. When `allowed_org_ids` is **empty** (Trusted Orgs OFF), all authenticated Verifiers can access the code and `is_restricted` is `false`. When `allowed_org_ids` is **non-empty** (Trusted Orgs ON), only listed organizations can verify; any other caller gets `is_restricted: true`. For all non-`active` statuses, `is_restricted` is always `false`.
5. **Credential detail fields** (`credential_id`, `owner_name`, `credential_type`) are populated only for rows where `status == "active"` AND `is_restricted == false`.
6. **Access logging**: `VerifiedLinkAccessLog` entry is written only for fully successful rows (active + non-restricted).
7. **`remaining_access_count` decremented** only for fully successful rows (atomic, same as single-verify).
8. **`batch_id`** is a UUID4 generated per request for client-side deduplication. Not stored in any database collection.
